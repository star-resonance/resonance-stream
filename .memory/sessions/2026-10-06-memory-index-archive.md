**Bridge packet limit -- the cause of `CS-restart-nodup` (2026-10-06, `claude/bridge-packet-limit`; Kade: "go to packet-limit fix"):** the manual `bridge-smoke.yml` run on `main` (run 37495056171, after #200) stopped at capture-spike, so chat-rules, persistence, download-integrity, translator-stub and popups did not run (their rows are still unread). Cause, from the app log: `Cannot send packet of size '108005'. It's greater than the broker's maximum packet size of: '10240'` -- `bridge/live.rs` built `MqttOptions` with rumqttc's default of 10 KiB, the app's answer to `get-chat-history` after the burst test (~108 KB) was refused, and the client reconnected, so the ack never came (the #190 / #191 diagnoses, "not slow start-up", were right about that and wrong to leave the cause open). Fix: `resonance_core::bridge::MAX_PACKET_BYTES` (16 MiB, 1 test red first) set for both directions in `live.rs`; `bridge::fit_ack` turns an answer over the limit into an error ack (a too-big publish would again reconnect and lose the ack; test red first); stand-in switch `FAKE_APP_PERSIST_BUG=small-packets` (drops an ack over 10 KiB) and persistence row **CP-big-ack** (300 GUILD lines, `get-chat-history` returns all of them) -- the stand-in could not show this before because it has no packet limit. Gates: core 495 tests green, app cross-checked (debug, `test-env`, release `test-env`), persistence pytest (see the commit body). NOT VERIFIED: the real app (the next manual `bridge-smoke.yml` dispatch on `main` must read capture-spike green, then the five skipped steps); whether the Node broker (aedes) has a packet limit of its own -- CP-big-ack on the real app answers that. **Still unread after that run: CP-fav-*, CR-ruby-* incl. the 一人 / 二人 / 一人前 reading (K16), TS-dict-* and the K8 `<bos>` count, popups, download-integrity.**
